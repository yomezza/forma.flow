# FORMA TELA — FRONTEND PROMPT / 01-specialists

## Роль и задача

Ты — frontend-разработчик FORMA TELA. Твоя задача — **реализовать работающую демонстрационную поддержку нескольких специалистов и кабинетов** в существующем статическом приложении на HTML/CSS/Vanilla JS. Логика должна соответствовать **утверждённой идее** и **спецификации архитектора**, опубликованной в GitHub. Не придумывай её с нуля и не заменяй её упрощённым «первый свободный специалист».

**Источники обязательны к чтению по ссылкам.** Это не обзор и не предложение просто «посмотреть документацию»: **открой каждую доступную ссылку, прочитай полный документ, сопоставь с фактическим кодом и используй его как рабочий контракт**. Если GitHub недоступен или файл отсутствует, сообщи об этом и не выдавай непроверенные предположения за требования архитектора.

## 2. Что сделать в DemoAPI

Оставить прежний статический стек, асинхронный `SiteAPI`, существующие API-функции и событие `forma-change`.

Реализовать **неразрушающую миграцию** с текущего `version:3` на `version:4` по `demo-data-migration.md`. Ключ **не переименовывать**: `formaTela.demo.v1`. Поддержать импорт старых JSON v1–v3, экспорт новой схемы, повторяемость migrate, валидацию, отказ без потери данных при невозможности сохранения.

Новые данные из спецификации архитектора: `revision`, `specialists`, `rooms`, `specialistServices`, `specialistSchedules`, `absenceRequests`, `accounts`, `demoSession`, `assignmentEvents`, `auditEvents`, `capacityExceptions`, дополнительные поля `booking.specialistId/roomId/assignmentUpdatedAt/completion`. Сохраняй исторические ID, цены, статусы, услуги, клиентов, графики и содержимое сайта. **Не назначай задним числом специалистов старым сеансам**.

Один активный специалист и один кабинет в стартовых демоданных; владелец имеет роли `admin` и `specialist`. У специалиста изначально доступны действующие услуги, как описано архитектором; дальше администратор может изменять их.

Оставить рабочими существующие `getAvailableSlots`, `createBookingRequest`, `getDateStates`, `confirmBooking`, расписание simple/advanced и остальные функции; при необходимости расширить внутреннюю валидацию. **Не создавать параллельный второй независимый источник доступности**.

### Существенное расхождение по клиентским телефонам

Текущий код и `docs/DEMO_API.md` требуют **уникального нормализованного телефона клиента**; в ранее согласованной логике проекта это тоже было утверждено. Но `gap-analysis.md` и `demo-data-migration.md` архитектора требуют **разрешать разные карточки клиентов с одним телефоном**, оставляя публичную заявку с `clientId:null` до выбора администратором.

**Не меняй эту часть модели молча.** До изменения уникальности, алгоритма создания клиента и `clientId` публичной заявки необходимо получить подтверждение владельца/архитектора, какое из правил является окончательным. Это отдельное бизнес-решение, не вытекающее из задачи о специалистах. Остальные независимые части `01-specialists` можно разрабатывать параллельно.

### Алгоритм назначения — не упрощать

Точное основание — [assignment-engine.md](https://github.com/yomezza/forma.flow/blob/backend-architecture/docs/backend/features/01-specialists/assignment-engine.md).

- Для каждой заявки рассматриваются доступные пары **(специалист, кабинет)** с учётом компетенций, опубликованного студийного графика, личных смен/исключений, утверждённых отсутствий, занятости и перерыва.
- Новую публичную заявку разрешать лишь при существовании совместного распределения **всех пересекающихся активных заявок**, включая неназначенные. Простая проверка «один специалист и один кабинет свободны» недостаточна.
- Пересечение времени: полуоткрытые диапазоны `[start,end)`; перерыв учитывается после окончания; связные компоненты по пересечениям, даже если первая и третья записи прямо не пересекаются.
- Реализовать чистую `solveAssignments` по указанному контракту с детерминированным поиском (MRV, forward checking, backtracking). Состояния `SAT/UNSAT/UNKNOWN`; исчерпание лимита поиска **не означает свободный слот**. Учти отдельное замечание архитектора о корректной обработке `UNKNOWN` при поиске ветвей.
- `getAvailableSlots` проверяет кандидатов по этой логике. `createBookingRequest` повторяет проверку непосредственно перед сохранением в существующем `change()`.
- При публичном создании **не назначать принудительно** `specialistId` и `roomId`; заявка резервирует вместимость логически, пока конкретная пара не закреплена.
- При административном назначении запрещать прямые нарушения; если назначение лишь косвенно делает неназначенные заявки невыполнимыми, показывать пострадавшие ID и требовать отдельного явного согласия. Сохранять события и предупреждения.
- Проблемные временные компоненты после подтверждённого косвенного конфликта блокируют новые заявки, **не весь день**. Изолированные допустимые интервалы не блокировать.
- Предпросмотр назначения и само сохранение должны проверять одну и ту же актуальную ревизию данных; устаревшее подтверждение не принимается автоматически.

Ограничения сложности, кэш, предельные размеры компонентов и причины отказов бери из документа архитектора, не подменяй своими значениями.

## 3. Раздел «Специалисты» у администратора

В существующем полноэкранном административном интерфейсе добавь пункт **«Специалисты»**. Не возвращай модальную админку; она уже заменена отдельным представлением.

Раздел должен позволять:
- Просматривать действующих и архивированных специалистов, их услуги, личные графики, связанные демо-аккаунты.
- Добавлять профиль нового специалиста (администратор создаёт и приглашает), редактировать его имя, перечень услуг, недельные часы и исключения; архивировать с сохранением истории.
- Управлять кабинетами (начально один), их доступностью и автоматическим назначением при закреплении записи.
- Видеть входящие заявки специалиста на выходной/отпуск, включая частичный день; **утвердить целиком** либо **отклонить с причиной**. До утверждения публичные слоты не изменяются.
- При утверждении отсутствия сохранять существующие записи и назначение, показывать «Требуется переназначение», если появились конфликты.
- Использовать компактный стиль FORMA TELA и `AdminDraftStore` для несохранённых форм, не смешивая их с утверждёнными изменениями графиков.

В карточке бронирования добавь назначение/переназначение исполнителя и кабинета, просмотр допустимых кандидатов, предпросмотр предупреждений, историю назначений. Нельзя переписать подтверждённость/завершённость записи при смене исполнителя. Переназначение разрешено до завершения (отменённые/завершённые — по контракту доменной логики не переназначаются).

На странице «Обзор» добавь компактный блок **«Требуют внимания»**: подтверждённые заявки без специалиста, необходимость переназначения, косвенный конфликт, запросы на отсутствие, иные причины из `domain-rules.md`. В разделе «Записи» отображай соответствующие небольшие индикаторы. Они вычисляемые и **не становятся новыми статусами** бронирования.

## 4. Отдельное пространство специалиста

Разработай самостоятельное представление с разделами:
- **Мои записи** — предстоящие (включая назначенные pending с пометкой «Ожидает подтверждения») и завершённые; другие записи скрыты.
- **Мой график** — личная неделя, администраторские исключения, утверждённые отсутствия в режиме просмотра.
- **Заявки на отсутствие** — форма целого дня, диапазона или части дня, список запросов, статус, отзыв только пока запрос pending.
- Историю **собственных событий переназначения** покажи в уместном небольшом подразделе/блоке, без чужих текущих записей.

У владельца, имеющего две роли, в шапке переключатель **«Администратор / Специалист»**. Доступные разделы меняются без перезагрузки и без утраты черновиков форм. В роли специалиста изменение собственных рабочих часов запрещено; даже собственный отпуск владелец сначала запрашивает как специалист и затем **вручную** утверждает в административном интерфейсе.

Данные специалисту выдавай **отдельными безопасными DTO**: имя клиента, услуга, дата, время, статус, но **без телефона, чужих записей, полной истории клиентов и административных заметок**. Недостаточно просто скрыть телефон через CSS, если данные уже переданы в объект представления. Помни: это только демо-симуляция приватности, не настоящая безопасность на localStorage.

Завершить сеанс вправе только назначенный специалист, если `status === 'confirmed'` и текущее время не раньше планового окончания. Ошибочную отметку можно отменить без срока с возвращением в `confirmed`; причина необязательна, но событие аудита обязательно. Не оставляй старую админскую кнопку завершения как обход этого правила.

Для новых сотрудников реализуй **учебную** процедуру выдачи временных реквизитов и экран первой смены пароля по `demo-data-migration.md`. Никаких настоящих паролей, хешей, токенов в localStorage или sessionStorage, никакой имитации реальной защищённой аутентификации.

## 5. UI/UX, совместимость, проверка

Сохраняй цвета бренда: зелёный `#284B35`, песочный `#D8C6A6`, светлый `#F8F5EE`, золотой акцент `#BE9D52`. Интерфейс спокойный, компактный, с тонкими кнопками, разумными отступами, доступными полями и мягкими переходами. Не переписывай пользовательский сайт без необходимости. Клиент по-прежнему **не выбирает** специалиста и кабинет.

Проверить: desktop, планшет, телефон; навигацию клавиатурой; `prefers-reduced-motion`; отсутствие двойных скроллов; доступность текстов и ошибок.

**Обязательные сценарии тестирования:**
1. Миграция v1/v2/v3 → v4 без потери записей, клиентов, цен, расписания и SVG/контента; повторная миграция не создаёт дубликаты; экспорт/импорт v4.
2. Один специалист + один кабинет: невозможно два пересекающихся сеанса.
3. Два специалиста + два кабинета с разными услугами: корректное распределение двух одновременных заявок, которое жадный алгоритм мог бы пропустить.
4. Частичные перекрытия и цепочки интервалов; перерывы; границы смен/отпусков.
5. Подтверждённая и pending запись без специалиста; назначение не меняет статус.
6. Косвенный конфликт: предупреждение с ID, явное подтверждение администратором, аудит, блокировка новых записей в проблемном компоненте, но не всего дня.
7. Утверждение отсутствия при существующем назначении: запись не удаляется, назначение сохраняется, есть предупреждение.
8. Архивирование специалиста с будущими назначениями: история сохранена, появляется требование переназначения.
9. Специалист видит лишь свои данные, не получает телефон; не может управлять чужими заявками или подтверждать их.
10. Завершение только после окончания подтверждённого сеанса; отмена завершения, журнал действий.
11. Учебные роли/первая смена пароля; отсутствие реальных секретов в хранилище.
12. Несохранённые формы и прежние простое/расширенное расписания продолжают работать.

Предусмотри воспроизводимые автоматизированные тесты чистой логики, особенно solver и миграции. Если архитектор опубликовал `demo-test-cases.md`, используй именно эти фикстуры; если нет — тестируй перечисленные в `assignment-engine.md` 11 граничных примеров и явно укажи, какие случаи ещё требуют спецификации.

## 6. Порядок выполнения

1. Сначала **открой GitHub-ссылки из раздела 1** и проверь актуальные ветки/файлы. Сделай короткое сравнение настоящего кода со спецификацией; отметь отсутствующие файлы и противоречия.
2. Определи, достаточно ли материалов для каждого модуля. При недостатке критичного контракта явно назови блокер; не выдавай догадки за решения архитектора. Для независимых модулей продолжай работу.
3. Реализуй миграцию v4, модели и базовую доменную логику с тестами; затем solver и изменения в availability/booking.
4. Добавь методы SiteAPI согласно опубликованной `demo-api-spec.md`, если она появилась, а иначе — строго документируй согласованные сигнатуры и вынеси неоднозначности на уточнение до связывания UI.
5. Реализуй интерфейс администратора, пространство специалиста, рассмотрение отсутствий и блок «Требуют внимания».
6. Проверь весь сквозной сценарий: клиент → заявка без специалиста → звонок/подтверждение → назначение кабинета и специалиста → личный кабинет → завершение → аудит.
7. Обнови `docs/DEMO_API.md` и README frontend, объясни v4, ограничения localStorage и поведение демо-аккаунтов. Не меняй Go/PostgreSQL и production OpenAPI: эта итерация архитектора подготовлена **только для демо**.
8. Публикуй готовый код и тесты в **`frontend`**. В итоговом ответе дай ссылки на коммиты/файлы и отчёт о пройденных и не пройденных тестах. Не заявляй о проверке на устройствах/браузерах, если не выполнял её.

**Критерий готовности:** администратор может управлять специалистами, компетенциями, кабинетами, назначениями и запросами на отсутствие; специалист видит собственные записи и выполняет разрешённые действия; система корректно вычисляет свободные слоты с учетом совместной размещаемости. Существующая онлайн-запись, календарь и демо-данные не сломаны. Неполные спецификации и открытые решения явно перечислены, а не скрыты.

Не начинай работу по памяти этого чата: **вся исходная бизнес-логика и разработанные архитектурные решения должны быть прочитаны по приведённым ссылкам на GitHub**.

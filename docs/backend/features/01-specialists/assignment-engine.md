# Движок совместной размещаемости — DemoAPI

Исходное требование: [нужно найти распределение **для всех пересекающихся заявок**, включая неназначенные](https://github.com/yomezza/forma.flow/blob/ideas/01-specialists/idea.md#L19-L25). Недостаточно проверить доступность специалиста и кабинета отдельно. Этот файл — спецификация чистого JS-алгоритма для демо, **не Go/backend**.

## Контракт

`solveAssignments(snapshot, {date, candidate, fixedOverrides = {}, excludedIds = [], nodeLimit = 50000})`

**Вход:** снимок неизменяемых данных, дата, кандидат (или `null` для проверки текущих заявок), закреплённые `specialistId/roomId` (nullable) у каждой действующей записи, опубликованное расписание студии, личные интервалы/компетенции, утверждённые отсутствия, активные кабинеты, `settings.breakMinutes`. Поле `candidate` содержит ID, услугу, локальные `date/time`, duration и status pending_confirmation.

**Результат:** `{feasible:boolean, uncertain:boolean, allocations:{[bookingId]:{specialistId,roomId}}, reason:string|null, examinedNodes:number, affectedBookingIds:string[]}`. `uncertain:true` при лимите поиска; **не интерпретировать как доступность**. Нельзя мутировать snapshot из `solveAssignments`.

**Типы времени:** целые минуты одной локальной даты; сеанс `[start,end)` должен целиком входить в рабочий интервал; занятый диапазон `[start,end+breakMinutes)`. Все пересечения полуоткрытые; касание после буфера не конфликт. Для сравнения времён DST в демо использовать явную временную зону кабинета, если настроена, и в тестах фиксированный clock; существующий браузерный режим помечать как ограничение демо.

## Строгие фильтры кандидатов

Для каждой заявки `b` построить домен пар `(specialistId,roomId)`:
- специалист `active`, его ID из `b.specialistId` при закреплении, он выполняет услугу, сеанс целиком внутри его недельных/админских интервалов и **за пределами** утверждённых отсутствий;
- кабинет `active`, ID из `b.roomId` при закреплении; если `null`, все доступные кабинеты допустимы;
- сеанс целиком в **опубликованном** студийном рабочем интервале, старт согласован с `step`; `advanced.drafts` вообще не участвует;
- ни при каком назначении нельзя обойти занятость уже закреплённого специалиста/кабинета или компетенцию.
- `pending_confirmation` и `confirmed` — обязательства. `cancelled` — исключить; `completed` — исторический факт, для публичных будущих слотов не участвует (новые completed возможны только после окончания).

Не достаточно `domains.every(domain => domain.length>0)`: две заявки могут требовать один и тот же ресурс одновременно.

## Разделение на независимые компоненты

Граф: вершины — записи с занятыми интервалами; ребро, когда диапазоны `[start, occupiedUntil)` пересекаются. Обработать **связные компоненты**, а не только заявки, которые прямо пересекаются с новым кандидатом: A пересекает B, B — C, хотя A и C не пересекаются. Если нет ребра — задачи независимы.

Для публичной заявки проверять связный компонент кандидата, с учётом всех закреплённых назначений/защищённых обязательств. Для предварительного календаря выполнять тот же алгоритм по каждой затронутой дате; не делать запрос на каждый слот из localStorage заново. Отсутствие новой заявки в компоненте не означает, что весь день недоступен.

## Точный алгоритм (псевдокод в стиле JS)

~~~js
function solveComponent(jobs, nodeLimit) {
  // jobs: {id, occupiedStart, occupiedEnd, domain:[[specialistId, roomId], ...]}
  // Чистая функция: домены построены предварительно из опубликованных правил.
  const jobsById = new Map(jobs.map(job => [job.id, job]));
  const chosen = new Map();
  let examined = 0;

  function consistent(job, pair) {
    return [...chosen].every(([otherId, other]) => {
      const b = jobsById.get(otherId);
      if (!overlaps(job, b)) return true;
      return pair[0] !== other[0] && pair[1] !== other[1];
    });
  }

  function dfs(unassigned) {
    if (unassigned.length === 0) return {result:'SAT', witness:new Map(chosen)};
    if (++examined > nodeLimit) return {result:'UNKNOWN'};

    // Minimum remaining values: выбрать заявку с наименьшим числом допустимых пар.
    const options = unassigned.map(job => ({
      job, valid: job.domain.filter(pair => consistent(job, pair))
    })).sort((a,b) => a.valid.length-b.valid.length || a.job.id.localeCompare(b.job.id));
    if (!options[0].valid.length) return {result:'UNSAT'};
    const {job,valid} = options[0];

    let hadUnknown = false;
    for (const pair of valid) {
      chosen.set(job.id,pair);
      const rest = unassigned.filter(x => x.id !== job.id);
      // forward-check: у каждой оставшейся задачи должна остаться хотя бы одна пара
      if (rest.every(x => x.domain.some(p => consistent(x,p)))) {
        const out = dfs(rest);
        if (out.result==='SAT') return out;
        if (out.result==='UNKNOWN') hadUnknown = true;
      }
      chosen.delete(job.id);
    }
    return {result: hadUnknown ? 'UNKNOWN' : 'UNSAT'};
  }
  const outcome=dfs(jobs);
  return {outcome, examinedNodes:examined};
}
~~~

`jobsById` — локальная map, построенная из всех `jobs`. Для закреплённой заявки `domain` имеет только пары с закреплённым специалистом/кабинетом, а не варианты для молчаливого переназначения. В сохранённом `booking` пара `specialistId/roomId` всегда **оба NULL либо оба заполнены**; частичное закрепление хранить нельзя. В предпросмотре назначение может прийти с `roomId:null` — это **запрос автоматического подбора**, а не частично сохранённая пара.

**Важное исправление для разработки:** при возврате `UNKNOWN` из одной ветви поиск можно продолжить по другим, но если ни одна не дала `SAT`, итог всё равно `UNKNOWN`, а не `UNSAT`; если найден `SAT`, его можно вернуть сразу. При лимите узлов нельзя выдавать ложный отказ «точно нет вместимости» — это отдельный `CAPACITY_CHECK_LIMIT`.

## Прямые конфликты и косвенный ущерб от админского назначения

`previewAssignment(bookingId, proposed)` сначала проверяет прямые условия **без override**:
- специалист некомпетентен/неактивен/в отпуске/вне смены → отказ;
- кабинет закрыт, закреплённый специалист или кабинет уже имеет пересекающееся другое закреплённое назначение → отказ;
- завершённую/отменённую запись перепривязать нельзя.

Далее временно закрепить выбранные пару/частичное назначение и выполнить `solveComponent` для затронутого множества. Если `SAT`: `{allowed:true, requiresConfirmation:false, roomId, affectedBookingIds:[]}`.

Если `UNSAT` из-за других **неназначенных** заявок — найти **минимальный** (по числу) набор таких заявок, удаление которых из поиска делает остальные выполнимыми. Перебирать только потенциально пострадавшие неназначенные заявки, по возрастанию количества исключений, с детерминированной сортировкой ID и строгим бюджетом; закреплённые заявки исключать запрещено. Если найдено: `{allowed:true, requiresConfirmation:true, affectedBookingIds:[...], reason:'INDIRECT_ASSIGNMENT_CONFLICT'}`. Если решения нет даже после исключения всех неназначенных: это прямой/системный конфликт → `allowed:false`. При `UNKNOWN` — только `CAPACITY_CHECK_LIMIT` без утверждения.

`assignBooking(..., {acknowledgedBookingIds, expectedRevision})` **повторяет** предпросмотр внутри атомарного `change()`, сравнивает ревизию, требует **точного совпадения** подтверждённых IDs с актуальным набором пострадавших, сохраняет действующее назначение, audit+assignment event, помечает вытесненные заявки. Ранее назначенные заявки не выбрасываются из поиска для улучшения результата.

## Безопасное правило для новых заявок после разрешённого ущерба

`capacityExceptions` содержит открытые проблемы после явного override (а также вновь выявленные после утверждения отсутствия или архивации). При запросе публичного слота:
1. Построить связный по занятости компонент, содержащий кандидата.
2. **Если он пересекается с открытой проблемной записью** (непосредственно или по цепочке занятых интервалов), вернуть `UNRESOLVED_CAPACITY_CONFLICT`; не пытаться компенсировать чужую невыполнимую заявку новой.
3. В остальных компонентах выполнить обычную полную проверку `solveComponent`; новые публичные заявки разрешены при `SAT`.
4. После ручного решения пострадавших записей заново пересчитать предупреждения и снять исключение, если все записи компонента стали выполнимы.

Правило консервативно: часть фактически свободных комбинаций **внутри проблемного компонента** временно недоступна. Зато не ухудшается существующий ущерб и не блокируются часы, не связанные пересечениями. Проблемы в одном временном компоненте **не закрывают весь день**.

## Автоматический кабинет

При создании **публичной** заявки `roomId:null`: свободная ёмкость резервируется условно, без произвольного закрепления кабинета, иначе один выбор может помешать будущему размещению. При явном назначении администратором `specialistId` и неуказанном `roomId`, engine перебирает активные кабинеты в устойчивом порядке `sortOrder,id` и выбирает первый, который не создаёт прямого или косвенного конфликта; если ни один не даёт нулевой ущерб — возвращает best preview с минимальным `affectedBookingIds` и требует подтверждения. Пользователь не выбирает кабинет.

Два одновременных публичных запроса в одном кабинете не становятся допустимыми: совместный solver вернёт `UNSAT` для второго. `roomId` до назначения сохраняется `null`, что не означает «кабинет свободен».

## Кэширование и лимиты

- Локальный `db.revision` увеличивается на каждую успешную запись; кэш `(revision,date,serviceId,slot)` для availability возможен в памяти одной вкладки. При `forma-change` сбрасывать кэш. Не сохранять рассчитанный witness в localStorage как «истину».
- Демонстрационная верхняя граница: `nodeLimit=50000`, не более 32 действующих заявок в одном компоненте, не более 12 активных специалистов и 8 кабинетов для синхронной проверки. Если превышено — `CAPACITY_CHECK_LIMIT`; не подтверждать новый слот. Не удалять уже существующие записи ради лимита.
- До начала поиска фильтровать нулевые домены, сортировать по размеру домена, учитывать фиксированные пары и пересечения, выполнять forward checking. При нескольких равноправных решениях выбирать устойчивый порядок ID.
- `getAvailableSlots` вычисляет список кандидатов по старому шагу/длительности, но пропускает только `SAT` после добавления **каждого** кандидата. `createBookingRequest` повторяет ту же проверку в `change()`; старый результат GET не гарантирует место.

## Граничные примеры

1. **1 специалист / 1 кабинет.** 10:00–11:00 занимает оба; второй сеанс в 10:30 не помещается.
2. **2 специалиста / 2 кабинета, разная квалификация.** S1 делает A и B, S2 только A; две заявки A+B на 10:00 требуют S2→A, S1→B. Жадный «первого свободного» мог назначить S1→A и ложно отвергнуть B; поиск возвращает SAT.
3. **2 неназначенные заявки с тем же временем.** В 2 кабинета, но 1 подходящий специалист → UNSAT.
4. **Частичное перекрытие.** A 10:00–11:00, B 10:45–11:30, при одном кабинете → UNSAT. При B 11:15 после буфера 15 → SAT.
5. **Цепочка A↔B↔C.** A 10–11, B 10:45–11:45, C 11:30–12:30: A и C не пересекаются, но все три должны попасть в **одну** компоненту.
6. **Косвенный конфликт.** S1 умеет A/B, S2 только A, две неназначенные записи A и B. Админ закрепляет A за S1 → B теряет единственного исполнителя. Прямого конфликта нет, показываем ID B, разрешаем только после явного подтверждения, блокируем новые заявки в проблемном компоненте.
7. **Одобренный отпуск.** Утверждение отсутствия S1 14–17 сохраняет запись с S1 на 15:00; причина REQUIRES_REASSIGNMENT, никакого автоматического переназначения.
8. **Архивирование.** Действующая запись остаётся, specialistId прежний, появляется предупреждение. Архивный профиль не входит в домен новых заявок.
9. **Переназначение.** Старый S1 занят, новый S2 доступен; проверка всех пар и кабинета, история с before/after, статус не меняется.
10. **Граница смены и перерыв.** Последний сеанс может закончиться ровно в конце смены, но следующий сеанс того же специалиста/кабинета не может начаться раньше окончания буфера.
11. **Нет решения в лимит.** Возвращать `CAPACITY_CHECK_LIMIT`, а не случайный свободный слот.

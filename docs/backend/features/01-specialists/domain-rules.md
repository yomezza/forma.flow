# Доменная логика демонстрации — идея 01

Первоисточник: [назначения](https://github.com/yomezza/forma.flow/blob/ideas/01-specialists/idea.md#L15-L26), [отсутствия](https://github.com/yomezza/forma.flow/blob/ideas/01-specialists/idea.md#L28-L34), [учётные записи/роли](https://github.com/yomezza/forma.flow/blob/ideas/01-specialists/idea.md#L36-L43), [завершение/аудит](https://github.com/yomezza/forma.flow/blob/ideas/01-specialists/idea.md#L45-L52). Это **целевая логика DemoAPI**, не изменение серверной архитектуры.

## 1. Сущности и отношения

- `Specialist`: независимый человек со стабильным `id`, `active|archived`, перечнем разрешённых услуг (через `specialistServices`) и своим недельным графиком.
- `Room`: отдельный ресурс, один сейчас, несколько в будущем. Поле `isActive`; физический кабинет нельзя занимать двумя пересекающимися сеансами.
- `Account`: демонстрационная оболочка логина/ролей. `roles` может одновременно содержать `admin` и `specialist`; `specialistId` связывает аккаунт с профилем. `activeRole` — режим показа рабочего пространства, не источник безопасности.
- `Booking`: сохраняет прежний `status`, снимок услуги/имени/телефона; новые поля `specialistId: string|null`, `roomId: string|null`, `assignmentUpdatedAt` и `completion`. `clientId:null` у нового публичного запроса до явного решения администратора. Назначение/подтверждение **не одно и то же**.
- `SpecialistSchedule`: 0..6 → интервалы `[{start,end}]`; дополнительно административные `overrides[YYYY-MM-DD]` на конкретные дни. И личные утверждённые `AbsenceRequest`, которые вычитаются из графика.
- `AbsenceRequest`: ожидает/утверждён/отклонён/отозван. Временные границы на один день или полный диапазон дат.
- `AssignmentEvent`, `AuditEvent`, `CapacityException`: отдельная неизменяемая история решений; предупреждения вычисляются заново.

## 2. Матрица доступа (симуляция для UI, НЕ авторизация)

| Действие | Посетитель | admin | specialist |
|---|---|---|---|
| Услуги, студийный календарь, свободные слоты, подать заявку | Да | Да | Да как посетитель |
| Получить всех клиентов и телефоны | Нет | Да | **Нет** |
| Просматривать неназначенные/чужие заявки | Нет | Да | **Нет** |
| Создать/архивировать специалиста, изменить услуги и рабочие часы | Нет | Да | Нет |
| Создать/изменить кабинет | Нет | Да | Нет |
| Предпросмотр и назначение специалиста/кабинета, переназначение | Нет | Да | Нет |
| Подтвердить/отменить бронирование, привязать карточку клиента | Нет | Да | Нет |
| Посмотреть свои назначенные заявки (pending и confirmed) | Нет | Да для всех | Только свои |
| Посмотреть свою завершённую историю | Нет | Да для всех | Только свои |
| Посмотреть события собственного переназначения | Нет | Да для всех | Только о **своём прошлом назначении** |
| Изменить свой недельный график или одобрить отсутствие | Нет | Да | Нет |
| Подать/отозвать своё отсутствие | Нет | Нет в роли admin | Да в роли specialist |
| Утвердить/отклонить отсутствие | Нет | Да, включая собственную заявку при двойной роли, но **только вручную** | Нет |
| Отметить свой подтверждённый сеанс выполненным / отменить свою отметку | Нет | Нет в роли admin | Да после планового окончания / отмена без срока |

Смена UI-роли не меняет аккаунт, `account.roles`; специалист не может получить чужой телефон даже через объект, возвращённый `getMyBookings()`. Телефон не должен попадать в `specialist` DTO, историю или QR.

## 3. Состояния заявок

| Из | В | Действие | Условия |
|---|---|---|---|
| — | pending_confirmation | Публичный createBookingRequest | Студия открыта, услуга активна, выполнимо распределение всех затронутых заявок |
| pending_confirmation | confirmed | admin.confirmBooking | Разрешено **без назначенного специалиста**, но карточка `clientId` уже связана администратором |
| pending_confirmation | cancelled | admin.cancelBooking | Причина опциональна, слот освобождён |
| confirmed | cancelled | admin.cancelBooking | Сохранять историю, слот освобождён |
| confirmed | completed | specialist.markMyBookingCompleted | Назначенный и активный специалист, `now >= plannedEnd`, статус confirmed |
| completed | confirmed | specialist.undoMyCompletion | **Тот специалист, кто завершил**, без срока; аудит обязателен |
| cancelled | pending_confirmation | admin.restoreBooking | Новая проверка всего множества назначений/слотов, статус остаётся pending |
| прочие | — | Отказ | `INVALID_STATUS_TRANSITION` |

**Нельзя:** завершить pending/cancelled, завершить до планового конца, администратору завершить вместо специалиста (даже если у него есть отдельная роль admin), автоматически отменить из-за отпуска/архивации. Админ меняет специалиста/кабинет пока booking не completed и не cancelled; само переназначение не меняет status. Отмена отметки completed восстанавливает confirmed и сохраняет исполнителя, который завершил.

## 4. Обязательные проверки при создании и назначении

1. Проверить структуру входа, роль и существование сущностей; валидировать календарную дату, время, ID и статус.
2. Проверить опубликованное расписание **студии**: режим simple (с блокировками и отпуском студии) либо advanced (только published); сеанс целиком помещается в одну опубликованную смену.
3. Проверить личный график назначаемого специалиста: разрешённая услуга, активность, интервалы недели, исключения, утверждённые отсутствия; висящая заявка на отсутствие **не влияет** на доступность.
4. Проверить выбранный/автоматически предлагаемый кабинет: активность, отсутствие прямого пересечения с закреплёнными назначениями; специалист также не должен быть занят другим закреплённым сеансом.
5. Проверить **совместную размещаемость** всех затронутых пересекающихся ещё не распределённых заявок, а не по одной; [алгоритм](assignment-engine.md).
6. Для админского назначения, которое вредит только другим **неназначенным** заявкам, показать точные ID и получить отдельное явное подтверждение. Другие прямые нарушения не разрешаются.
7. Если из-за отсутствия/архивации ранее закреплённое назначение стало недопустимым, сохранить запись и назначение, пометить `requires_reassignment`. Новые закрепления на недоступного специалиста запрещены.

### Разница между предупреждением и запретом

| Код причины | Причина | Новое публичное бронирование | Админская операция |
|---|---|---|---|
| `NO_QUALIFIED_SPECIALIST` | Никто не оказывает услугу/не работает | Отказ | Не назначать |
| `ROOM_UNAVAILABLE` | Нельзя разместить в кабинетах | Отказ | Не занимать занятый кабинет |
| `SPECIALIST_BUSY` | Закреплённый специалист занят | Отказ | Не назначать одновременно |
| `SPECIALIST_OFF` | Смена/утверждённое отсутствие/архив | Отказ | Не создавать прямое нарушение |
| `GLOBAL_CAPACITY_CONFLICT` | Каждая заявка поодиночке выполнима, вместе — нет | Отказ | Только косвенный ущерб неназначенным может быть принят явно |
| `INDIRECT_ASSIGNMENT_CONFLICT` | Админским назначением вытеснены неназначенные | Не создавать новые записи в затронутом компоненте | Можно подтвердить ID пострадавших |
| `REQUIRES_REASSIGNMENT` | Существующее закрепление нарушено сменой условий | Заблокировать затронутый компонент до разбора | Показать варианты замены, не переназначать автоматически |
| `UNASSIGNED_SPECIALIST` | Действующая запись без исполнителя | Может быть допустимой, если solver найдёт размещение | Блок «Требуют внимания» |
| `ABSENCE_REVIEW_PENDING` | Нерассмотренный запрос специалиста | Не ограничивает слоты | Показать счётчик администратору |

Сообщения должны быть понятны пользователю: публично «На это время нет свободных мест» без имён персонала и внутренних причин; детали — только администратору.

## 5. Отсутствия, графики, архивирование

- Рабочие интервалы задаёт **только** администратор, включая исключения. Интервалы сортируются, `start < end`, не пересекаются и внутри одного календарного дня. Незапланированное на конкретную дату отсутствие личного override означает применение недели, а не закрытие студии.
- Специалист подаёт `kind:day_off|vacation`, `scope:full_days|partial_day`. Для `partial_day` — ровно одна дата и `start<end`, для `full_days` — включительный диапазон дат.
- `pending → approved` (администратором, целиком), `pending → rejected` (обязательная причина) или `pending → withdrawn` (тем же специалистом); другие переходы запрещены. После утверждения/отклонения отозвать нельзя.
- Пока `pending`, доступность не меняется. При утверждении утверждённые промежутки вычитаются из личной доступности. Если есть действующие назначения в этот период — `ABSENCE_CONFLICT` с ID; явное подтверждение позволяет утвердить и записать аудит, но **не снимает назначения**.
- При архивации специалиста его будущие назначения остаются исторически связанными, но получают `REQUIRES_REASSIGNMENT`; админ выбирает новую кандидатуру вручную. Архивированный персонал не предлагается для новых назначений.
- Отдельный кабинет можно отключить; его существующие назначения отмечаются `ROOM_INACTIVE`. В текущем демо один кабинет, поэтому ни два пересекающихся сеанса, ни два одновременных массажиста реально невозможны.

## 6. Блок «Требуют внимания»

`getAttentionItems()` возвращает вычисленные элементы с `bookingId`, `code`, `severity`, `hint`, `relatedRequestId?`. Для заявок в статусе pending/confirmed считаются: `UNASSIGNED_SPECIALIST`, `REQUIRES_REASSIGNMENT`, `NO_AVAILABLE_SPECIALIST`, `INDIRECT_ASSIGNMENT_CONFLICT`. Для запросов отсутствия: `ABSENCE_REVIEW_PENDING`. Отдельно сохраняется старый `OUTSIDE_STUDIO_SCHEDULE`. Одна карточка может иметь несколько причин; вычисления не меняют статус.

У специалиста не показывать блок чужих проблем; только собственные назначения и свою историю.

## 7. Неподлежащие переопределению инварианты

- Клиент не выбирает специалиста; статус подтверждения и факт назначения независимы.
- Один конкретный специалист и один конкретный кабинет не могут иметь два **одновременно закреплённых** пересекающихся действующих бронирования.
- Нельзя создать новую публичную заявку без решения совместной задачи распределения.
- Нельзя скрыть невыполнимость предварительного запроса без предупреждения после разрешённого исключения.
- Нельзя удалять записи, события и идентификаторы при смене графика/отпуске/архивировании.
- Все возвращаемые специалисту списки **формируются отдельным DTO**, а не `{...booking, clientPhone:undefined}` после передачи общих массивов.
- `localStorage`/кнопка «Роль» — только симуляция доступа, не гарантия конфиденциальности, безопасности и синхронизации.

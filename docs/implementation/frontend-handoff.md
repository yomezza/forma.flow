# Подключение frontend к backend

Backend реализует закреплённый [OpenAPI](../../backend/api/openapi.yaml)
из `backend-architecture` @ `160f0df`: 79 операций, 64 пути. Работа frontend
остаётся в отдельной ветке; её файлы здесь не менялись.

1. Сохранить асинхронный фасад SiteAPI; HTTP-адаптер вызывает `/api/v1/*` на
   том же origin. Для списков распаковывать `{items,nextCursor}`, загружать
   следующие страницы с `cursor` и `limit` (1–100). Не возвращаться к полной
   выгрузке всех клиентов/записей при каждом открытии списка.
2. Публичная форма выбирает услугу, дату и время. Она не отправляет specialistId,
   roomId или clientId. Добавить consentAccepted/consentVersion и один случайный
   Idempotency-Key на попытку; сохранять ключ при неоднозначной сетевой ошибке.
   Новый запрос — 201, повтор — 200 с исходной receipt, без телефона и назначений.
3. `GET availability/slots` — только предпросмотр. SLOT_UNAVAILABLE требует
   обновления слотов. CAPACITY_CHECK_LIMIT (503) означает, что сервер не доказал
   доступность; не показывать такой слот как гарантированный.
4. Вход всех сотрудников: `POST auth/sessions` с email/password. Cookie
   `ft_session` — HttpOnly; запросы отправлять с `credentials:'same-origin'`.
   CSRF брать из Session.csrfToken и передавать `X-CSRF-Token` на записи,
   включая logout и смену пароля. Origin проверяется сервером. В браузере он
   устанавливается автоматически; скриптовый HTTP-клиент должен передавать его.
5. При mustChangePassword=true доступны только current-session, logout и
   password/change. Приглашение создаёт аккаунт, но не отправляет письмо.
   Временный пароль показывается администратору единственный раз; не сохранять
   его в localStorage, логи, аналитические события или QR.
6. Один телефон может иметь несколько карточек. Даже единственный результат
   by-phone нельзя автоматически привязывать. Явно выбрать UUID либо создать
   карточку через PUT bookings/{id}/client, затем подтвердить запись.
   Подтверждение не требует назначения специалиста; snapshots заявки неизменны.
7. Назначение отдельно: candidates → preview → PUT assignment. Сохранять
   expectedCapacityRevision и точный acknowledgedBookingIds. RoomId=null
   разрешает автоматический выбор. При устаревшей ревизии заново показать
   предпросмотр; не подтверждать новые конфликты автоматически.
8. Для dual-role аккаунта выбор рабочего пространства хранится в UI. Путь
   `/specialist/me/*` задаёт контекст специалиста, а `/admin/*` — администратора.
   Права сервер читает из БД, а не из выбранной UI-роли или произвольного заголовка.
   Специалистский DTO никогда не содержит телефон/UUID клиента. После
   переназначения прежний специалист видит только обезличенное событие.
9. Подтвердить/отменить/восстановить — admin API. Завершить и отменить собственное
   завершение — specialist API. Завершение до ends_at отклоняется. Admin-ручки
   «завершить вместо специалиста» нет. Расписание/отпуска не отменяют записи.
10. Студийные изменения используют expectedRevision, назначения и отсутствия —
    expectedCapacityRevision, личная неделя PUT — возвращённое поле revision.
    Schedule history restore копирует исторические правила в drafts, не публикует.
    Для недельных правил формируется 366 дней вперёд по локальной дате студии;
    исторические датированные правила также сохраняются в черновиках. Дальше
    администратор выборочно публикует нужный диапазон. Несохранённые формы UI
    по-прежнему отдельны от серверных черновиков расписания.

Ошибки: `{error:{code,message,requestId,details}}`; детали SQL/PII наружу не выдаются.
Персональные/admin/auth ответы помечены no-store. Нет публичного чтения заявки
по ID или телефону, demo reset/import/clear/hard delete API. Экспорт — owner-only
с аудитом. Существующие `.ics`, Google Calendar и QR остаются задачей frontend;
не включать в них телефоны и внутренние ID специалистов/клиентов.

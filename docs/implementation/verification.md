# Проверки backend FORMA TELA

Проверки выполняются на реальной PostgreSQL 16 в изолированных временных БД.
Данные синтетические. Для полного повторения нужны INTEGRATION_DATABASE_URL,
PG_TEST_CONTAINER и Python-зависимости из backend/tests/requirements.txt.
Без этих параметров пропуск интеграционных тестов не означает успешную приёмку.

## Выполненные сценарии

- Чистые Go-тесты solver: SAT/UNSAT/UNKNOWN, фиксированные назначения,
  жадная ловушка, транзитивные компоненты и границы буфера. Дополнительно
  150 воспроизводимых случайных задач сравнены с полным перебором.
- Расписание: simple/advanced, разрыв между интервалами, черновик не виден
  посетителю, заблокированные даты, отпуск, личное отсутствие, DST gap/fold.
- PostgreSQL: четыре миграции с нуля; повторный Up; Down/Up в одноразовой БД;
  FK, пара nullable assignment, согласованность duration/buffer, два EXCLUDE.
- Двадцать конкурентных заявок: один кабинет → одна принятая заявка;
  два подходящих специалиста и два кабинета → две принятые заявки.
- Два отдельных OS-процесса с независимыми пулами: студийный lock сохраняет
  вместимость; двадцать одинаковых ключей дают одну заявку и одинаковые receipt.
- Конкурентные SQL UPDATE, обходящие сервис намеренно: один из конфликтующих
  назначений завершается SQLSTATE 23P01 отдельно для специалиста и кабинета.
- Общий телефон у нескольких UUID, ручная привязка карточки, независимые истории;
  подтверждение без карточки отклонено, подтверждение без специалиста разрешено.
- Session cookie, CSRF, first-login gate, смена пароля и отзыв старой сессии;
  специалист не получает телефоны, UUID клиентов и чужие текущие записи.
- Назначения и косвенное вытеснение: точное подтверждение ID, история, сохранение
  статуса; новые заявки в проблемном компоненте блокируются, соседние работают.
- Завершение только собственным назначенным специалистом после ends_at;
  отмена собственной отметки через месяц с сохранением событий.
- Отсутствия: pending не включён в опубликованную доступность, approved сохраняет
  запись и создаёт предупреждения; независимый конфликт не попадает в preview.
- Публикация: stale revision не записывает изменения; конфликты требуют
  подтверждения; history restore сохраняет черновик без автоматической публикации.
  Гонка публикации с заявкой сериализуется студийной блокировкой.
- Принудительные ошибки после INSERT: нет частичной заявки, idempotency row
  или осиротевшей новой клиентской карточки.
- Настоящий pg_dump/pg_restore в отдельную БД: схема, данные и idempotency replay
  сохранены. На 100000 строк проверены EXPLAIN с индексом и SQL-пагинация HTTP.
- Успешные запросы ко всем 79 операциям OpenAPI; входные и выходные схемы
  независимо проверены Python jsonschema (Draft 2020-12), включая форматы.
  Отдельные отрицательные HTTP/JSON тесты проверяют неизвестные поля,
  повторяющиеся ключи, согласие, размеры тела, роли и ошибки.

## Команды

Из backend/ с настроенными тестовыми переменными:

```sh
go mod verify
go vet ./...
go test -count=1 ./...
go test -race -count=1 ./...
make generate
git diff --exit-code -- internal/transport/http/routes.go internal/transport/http/schemas.json
govulncheck ./...
```

go test -race проверяет гонки Go отдельно от проверок конкурентности PostgreSQL.
CI настроен для PostgreSQL 16 и 18; конфигурация workflow сама по себе не является
подтверждением результата удалённого запуска.

## Toolchain и зависимости

Исходная архитектура фиксировала Go 1.27.3. При повторном сканировании 11 ноября
2026 обнаружена GO-2026-6859 в net/http, исправленная в Go 1.27.4:
https://pkg.go.dev/vuln/GO-2026-6859 . Минимальный toolchain, Dockerfile и CI
обновлены до 1.27.4; это исправление безопасности в той же архитектуре.

В golang.org/x/crypto сканер также отмечает неиспользуемый пакет openpgp
(GO-2026-5932). Backend использует argon2 и не импортирует openpgp; это отличается
от обнаружения вызываемой уязвимой функции. Итог сканирования фиксируется отдельно.

## Границы готовности к эксплуатации

API реализован, frontend в эту задачу не подключался. До публичного запуска
нужны реальные IANA TZ, каталог, персонал/квалификации, графики и адрес студии.
Bootstrap создаёт закрытый график и не придумывает специалистов.
Нужны TLS/ingress, отдельные DB-роли, политика хранения персональных данных,
зашифрованные резервные копии и общий ingress rate limit нескольких инстансов.
Эти настройки не заменяют серверные проверки и не открывают демо-reset/import API.

# DemoAPI / SiteAPI

Документ описывает frontend-контракт `dist/js/demo-api.js`. Все методы асинхронные и возвращают Promise. UI обращается к данным только через `SiteAPI`, сейчас это псевдоним `DemoAPI`. Демонстрационное хранилище localStorage с ключом `formaTela.demo.v1` не синхронизируется между посетителями.

## Сущности

- **Service**: id, name, description, durationMinutes, priceAmount, currency, sortOrder, isActive, visualSymbol.
- **Booking**: id, serviceId, снимок name/durationMinutes/priceAmount/currency, date (`YYYY-MM-DD`), time (`HH:mm`), status, опциональные clientId/clientName/clientPhone, createdAt/updatedAt и поля переходов статуса.
- **Client**: id, fullName, phoneNormalized в формате `+7##########`, createdAt, updatedAt.
- **Schedule**: `settings` хранит простой недельный график, блокировки и vacations. `schedule.activeMode` выбирает `simple` или `advanced`. В расширенном режиме published и drafts — словари правил по дате, history — до 30 изменений.
- **Day rule**: kind `working | off | unplanned`, intervals — упорядоченные непересекающиеся пары start/end, stepOverride — число минут или null.
- **Vacation**: id, startDate, endDate. Даты включительны. Пересечение периодов запрещено.

## Требования к будущему backend

Сохранить асинхронный контракт и смысл ответов. Операцию «проверить слот + создать/найти клиента + создать заявку + зафиксировать снимок услуги» сделать транзакционной и защищённой от дублей/пересечений. Публикацию диапазона, переключение режима, обновление отпуска и историю изменений тоже выполнять атомарно. Авторизовать административные методы на сервере. Время кабинета, часовой пояс и конфликт между предпросмотром и публикацией должны обрабатываться сервером.


## DemoAPI v4 — текущие изменения

Ключ localStorage остаётся `formaTela.demo.v1`, схема данных — `version: 4`. Миграция добавляет `revision`, профили специалистов, кабинеты, расписания, заявки на отсутствие, учебные аккаунты и журналы. При миграции v3 создаётся один активный профиль и один кабинет. Записи из старой базы не получают специалиста задним числом.

Публичная заявка через `createBookingRequest(data)` резервирует время и сохраняет имя и телефон как снимок заявки. `clientId` остаётся `null`. Администратор ищет все карточки с номером через `findClientsByPhone(phone)`, вручную связывает существующую или новую карточку через `assignBookingClient(bookingId, choice)`, затем подтверждает её методом `confirmBooking(bookingId)`. Подтверждение без связанной карточки возвращает `CLIENT_LINK_REQUIRED`. Одинаковый номер допустим у разных карточек клиентов.

Доступные слоты и кандидатные назначения проверяет `FormaAssignmentEngine.solveAssignments`. Matcher учитывает опубликованное расписание студии, график и квалификации специалиста, активность кабинета, утверждённые отсутствия и пересечение занятых интервалов. Черновики advanced-расписания в публичную доступность не входят. При достижении лимита поиска результат `UNKNOWN`, новый слот не предлагается. Назначение выполняется через `getAssignmentCandidates`, `previewBookingAssignment` и `assignBooking` с проверкой `expectedRevision`.

| `getSpecialists(options)`, `createSpecialist(data)`, `updateSpecialist(id, data)`, `archiveSpecialist(id)` | Просмотр, создание и архивирование профиля. |
| `setSpecialistServices(id, serviceIds)`, `getSpecialistSchedule(id)`, `setSpecialistSchedule(id, data)` | Квалификации и личный недельный график. |

| `getAssignmentCandidates(id)`, `previewBookingAssignment(id, data)`, `assignBooking(id, data)`, `getBookingAssignmentEvents(id)` | Предпросмотр, сохранение назначения и его история. |

Полный контракт v4 и целевые ограничения находятся в документах архитектора в `backend-architecture`. Не все сценарии архитектора реализованы и проверены в текущей версии.


## Косвенные конфликты и открытые исключения ёмкости

`previewBookingAssignment` сначала проверяет прямую допустимость назначения и совместное размещение связанного компонента. Если назначение допустимо само по себе, но вытесняет одну или несколько неназначенных заявок, результат содержит `requiresConfirmation: true` и точные `affectedBookingIds`. `assignBooking` требует `expectedRevision` и точного списка `acknowledgedBookingIds`. Без полного совпадения возвращается `CONFLICT_ACK_REQUIRED`; прямой конфликт с уже закреплённой записью не подтверждается.

После явно подтверждённого назначения создаётся `capacityException`:

```js
{
  id,
  createdByEventId,
  bookingIds,
  reason: 'INDIRECT_ASSIGNMENT_CONFLICT',
  createdAt,
  resolvedAt: null
}
```

Публичная доступность блокирует новые заявки в связанном компоненте с открытым исключением и возвращает пустой список слотов для затронутого времени. После исправляющего ручного назначения matcher пересчитывает компонент и заполняет `resolvedAt`, когда он снова выполним. Такие исключения отражаются в `getAttentionItems()`.

Проверки этой итерации находятся в `tests/idea01/assignment-engine.html` и `tests/idea01/api-capacity.test.js`. Наборы покрывают тринадцать сценариев matcher (границы буфера, connected-компоненты, закреплённые назначения, порядок входных данных) и API-сценарии миграции, внимания, предупреждений графика, частичного отсутствия, privacy DTO и косвенного конфликта.


## Дополнение: специалисты, личный график и privacy DTO

`getSpecialistSchedule(id)` возвращает недельные интервалы и исключения профиля, его собственную `revision` и `dataRevision` базы. Для `setSpecialistSchedule(id, {week, overrides, expectedRevision})` передавайте `dataRevision` из чтения: при параллельном изменении API вернёт `STALE_REVISION`. В административном разделе график редактируется по дням и допускает несколько непересекающихся интервалов в день; перечень услуг и имя профиля меняются отдельно.

Заявка специалиста поддерживает `scope: 'full_days'` или `scope: 'partial_day'`. Для частичного отсутствия укажите одну дату и `startTime`/`endTime`; для целых дней передайте `startTime: null` и `endTime: null`. До решения администратора заявка не влияет на публичные слоты. Форма специалиста показывает оба режима.

Ответы `getMyBookings`, `markMyBookingCompleted` и `undoMyCompletion` используют ограниченный DTO: имя клиента, услуга, дата, время, статус и название кабинета. Телефон, идентификатор карточки, заметки администратора и внутренние поля бронирования в этих ответах отсутствуют.

Это обеспечивает только безопасное разделение данных в интерфейсе демо. localStorage остаётся доступным любому скрипту в браузере и не заменяет backend авторизацию.

### Ревизии и назначение

`getAssignmentCandidates(id)` возвращает по одному элементу на специалиста: `roomIds` содержит допустимые кабинеты для текущей заявки, `requiresConfirmation` и `affectedBookingIds` описывают косвенные последствия, а `reasons` перечисляет причины отсутствия подходящих назначений. Интерфейс раскрывает пары «специалист — кабинет» и повторно получает точный preview перед сохранением.

Для `assignBooking`, `approveAbsence`, `rejectAbsence` и `setSpecialistSchedule` требуется актуальный `expectedRevision`; UI получает его через соответствующий preview или `getSpecialistSchedule`. Отменённую или завершённую запись нельзя переназначить. Подтверждение отсутствия принимает только точный набор ID конфликтующих бронирований.

### Элементы внимания

`getAttentionItems()` возвращает по каждой проблеме `code`, `bookingId` либо `relatedRequestId`, `severity`, `hint` и короткое `message`. В частности, неназначенная активная запись получает `UNASSIGNED_SPECIALIST`; если её нельзя разместить даже отдельно по текущим квалификациям, графикам и ресурсам, добавляется `NO_AVAILABLE_SPECIALIST`. Если matcher вернул неопределённый результат из-за лимита поиска, API не объявляет отсутствие специалиста. Предупреждения вычисляются без смены статуса записи.
